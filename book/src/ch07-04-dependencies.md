# Dependencies and the lock file

**This section teaches** how to make one package depend on another, and how the compiler pins what it found so
that every build uses the same code. It assumes [A package and its manifest](./ch07-01-package-and-manifest) and
[Imports](./ch07-03-imports), whose packages it uses: the library `tally` and the program `report`, in two
directories side by side.

## A dependency by path

<span class="listing-caption"><strong>Listing 7-21</strong>, <code>report/ceesafe.toml</code>: A program that depends on the library in the directory beside it.</span>

```toml
[package]
name = "report"
version = "0.1.0"
kind = "executable"
ceesafec = ">=0.40.0"

[dependencies]
tally = { path = "../tally" }
```

Each line of `[dependencies]` is one **dependency**: a library this package uses. The key, `tally`, is the
library's name. The value says where it is. `path` is a directory, relative to this manifest, that holds the
library's own `ceesafe.toml`.

::: tip Rule
A dependency's key is the `name` in the dependency's own manifest, and the dependency must be a library.

*Specification: `tooling.md` §4.1.*
:::

A path dependency is code you work on beside the program. Change a file in `../tally` and the next
`ceesafec check` in `report/` sees the change.

## `ceesafec fetch` and `ceesafe.lock`

A manifest with a dependency is not enough to build. Run `ceesafec check` in `report/` now and it stops:

```text
ceesafe.toml:1:1: error[N0324]: there is no ceesafe.lock: run 'ceesafec fetch'
  |
1 | [package]
  | ^
```

```sh
ceesafec fetch
```

```text
ceesafec: ceesafe.lock: 1 dependency
```

`fetch` finds every dependency, and the dependencies of those, and writes what it found to `ceesafe.lock`, beside
the manifest. That is the **lock file**:

<span class="listing-caption"><strong>Listing 7-22</strong>, <code>report/ceesafe.lock</code>: What <code>ceesafec fetch</code> wrote. You do not edit this file.</span>

```toml
# Written by ceesafec fetch (spec/tooling.md §4.3). Commit it with ceesafe.toml.

[[package]]
name = "tally"
source = "path+../tally"
```

Now `ceesafec check`, `run --interp` and `build` work. They read the lock file and never change it. Only `fetch`
writes it.

::: tip Rule
`ceesafec fetch` resolves the dependencies and writes `ceesafe.lock`. Every other command uses the lock file as it
is, and fails with `N0324` if it is missing or no longer agrees with the manifest. Run `fetch` after each change
to `[dependencies]`, and commit `ceesafe.lock` with `ceesafe.toml`.

*Specification: `tooling.md` §4.3.*
:::

A package with an empty `[dependencies]` needs no lock file.

## A dependency by git

A library need not be on your disk. A dependency can name a git repository:

```toml
[dependencies]
tally = { git = "https://example.org/tally.git", tag = "v0.1.0" }
```

Beside `git` goes exactly one of `tag`, `branch` or `rev` (a commit id). The library is the package at the top of
that repository. `ceesafec fetch` runs `git` to get it, and the lock file records what it got:

```toml
[[package]]
name = "tally"
source = "git+https://example.org/tally.git"
commit = "fbc1c20d789f21595ab36c0d71229a81e7124450"
hash = "sha256:bd78a12152473abe80b12dcfafbcd007665696e1b9e5cdcf0b1b8c5a37fc8de2"
```

- `commit` is the commit that the tag named when `fetch` ran. Builds use that commit from then on. If the tag or
  the branch moves later, nothing changes until you run `fetch` again.
- `hash` is a SHA-256 of the library's manifest and source files. Every command checks the files against it, so
  code that changed behind the lock file is an error (`N0325`), not a surprise.

The repositories and the checked-out commits are kept in a cache in your home directory, `~/.ceesafe`, or in the
directory the environment variable `CEESAFE_HOME` names. Nothing from a dependency runs during a fetch or a build:
packages have no build scripts.

## A dependency from the registry

The third form gives no location, only a **version requirement**:

```toml
[dependencies]
tally = "0.1"
```

`fetch` looks the name up in a package **index**, which is a git repository that lists the published versions of
each library. The default index is `https://github.com/CeeSafe/CeeSafe-index`, and the environment variable
`CEESAFE_INDEX` names another. `fetch` chooses the newest version that satisfies every requirement on the library,
and the lock file records the version, its repository, its commit and its hash.

A second `fetch` keeps a locked version while it still satisfies the manifest, even when a newer one has been
published. `ceesafec fetch --update` chooses the newest again for every library, and `ceesafec fetch --update tally`
for one.

## Version requirements

A version is three numbers, `MAJOR.MINOR.PATCH`. A requirement says which versions will do:

| Requirement | Versions it accepts |
|---|---|
| `"1.4"`, `"^1.4"`, `"^1.4.2"` | from that version up to, not including, `2.0.0` |
| `"0.3"` | from `0.3.0` up to, not including, `0.4.0` |
| `"=1.4.2"` | exactly `1.4.2` |
| `">=1.4"`, `">1.4"`, `"<2"`, `"<=1.9.3"` | by comparison; a missing number is 0 |
| `">=1.4, <1.8"` | both parts must hold |
| `"*"` | any |

A bare version is the first row: it accepts later versions with the same major number. Below `1.0.0` the minor
number plays that part, so `"0.3"` does not accept `0.4.0`.

## The compiler requirement

The `ceesafec` field of `[package]`, in Listing 7-21, is a requirement of the same form, on the compiler. It is
checked when the manifest is read, the manifest of each dependency too. Listing 7-21 with `">=0.99.0"` on line 5,
read by `ceesafec` 0.40.0:

```text
ceesafe.toml:5:12: error[N0321]: this package needs ceesafec >=0.99.0; this is ceesafec 0.40.0
  |
5 | ceesafec = ">=0.99.0"
  |            ^^^^^^^^^^
```

Set it when your code uses something a release added. A reader with an older compiler then gets this message in
place of an error about a name the old compiler does not know.

## `--offline`

`ceesafec fetch --offline`, and `check`, `run` and `build` with `--offline`, never use the network. They work with
what is on disk: path dependencies, and whatever the cache already holds.

For path dependencies alone that is everything, so `ceesafec fetch --offline` always succeeds for `report` as
Listing 7-21 has it. For a git or registry dependency it succeeds once the commit is in the cache, and until then
it fails with `N0323`, which the last mistake below shows.

## Mistakes

::: warning Mistake: changing `[dependencies]` without fetching
Add a second line to Listing 7-21, `ledger = { path = "../ledger" }`, and run `check`. The lock file is now behind
the manifest.

```text
ceesafe.toml:9:1: error[N0324]: ceesafe.lock does not record 'ledger' as the manifest names it: run 'ceesafec fetch'
  |
9 | ledger = { path = "../ledger" }
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
```

Run `ceesafec fetch`. The same code reports a lock file that is missing, and one whose locked version no longer
satisfies a requirement you changed.
:::

::: warning Mistake: a key that is not the library's name
You do not choose what to call a dependency. The library's manifest does.
:::

<span class="listing-caption"><strong>Listing 7-23</strong>, <code>report/ceesafe.toml</code>: The library in <code>../tally</code> is named <code>tally</code>, not <code>counts</code>. <code>ceesafec fetch</code> refuses this.</span>

```toml
[package]
name = "report"
version = "0.1.0"
kind = "executable"
ceesafec = ">=0.40.0"

[dependencies]
counts = { path = "../tally" }
```

```text
ceesafe.toml:8:1: error[N0322]: the package at the source of 'counts' is named 'tally'
  |
8 | counts = { path = "../tally" }
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
```

Use the name the message gives. `N0322` is also the code for a `path` that holds no `ceesafe.toml`.

::: warning Mistake: `--offline` before anything is fetched
`--offline` cannot get a repository it has never seen. With the git dependency of this section and an empty cache:

```text
ceesafe.toml:8:1: error[N0323]: 'https://example.org/tally.git' is not in the cache, and --offline forbids fetching it
  |
8 | tally = { git = "https://example.org/tally.git", tag = "v0.1.0" }
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
```

Run `ceesafec fetch` once with the network. After that, `--offline` works.
:::

::: details Coming from Rust
`ceesafe.lock` is `Cargo.lock`, and a requirement such as `"1.4"` means what it means to Cargo. Two things
differ. The build never writes or updates the lock file: `ceesafec fetch` does, and a stale lock is an error. And
there is one version of a package in a build, never two.
:::

::: details Coming from Go, TypeScript or Python
`ceesafec fetch` is `go mod download`, `npm install` or `pip install`, and `ceesafe.lock` is `go.sum` or
`package-lock.json`. There is no directory of downloaded packages inside your package: git and registry
dependencies live in one cache for all your packages, and nothing of theirs runs when they are installed.
:::

## Summary

- `[dependencies]` names libraries by `path`, by `git` with one of `tag`, `branch` or `rev`, or by a version
  requirement looked up in the registry's index.
- The key is the library's own name (`N0322` if not).
- `ceesafec fetch` writes `ceesafe.lock`; every other command only reads it, and a missing or stale one is `N0324`.
- For a git or registry dependency the lock file pins a commit and a hash of the files.
- `fetch --update` moves registry dependencies to their newest versions that fit.
- `--offline` uses only the disk and the cache (`N0323` if something is not there).
- `ceesafec = ">=…"` in `[package]` says which compilers can build the package (`N0321` if yours cannot).

This is the end of chapter 7. A program can now be many files and many packages. Chapter 8 turns to the
collections that the built-in library gives every one of them.
