# ADR 0127 — `ceesafec cbind`: the C binding generator as a command of the compiler

- Status: **Accepted** by the owner, 2026-11-13 ("Go ahead with the first three"), implemented on branch
  `impl/0127`; not yet released. Raised by the writers of the language's book (chapter 20; gaps2 D14): the generator
  of `extern "C"` blocks is `tools/cbind.py`, in CeeSafe's repository, and a user who installed a released
  `ceesafec` has neither the script nor, necessarily, Python, so they write the blocks by hand.
- Scope: the driver (`src/tooling/cbind.cee`, a new command; `src/main.cee`, the usage text and the dispatch);
  `src/support/json_tree.cee` (a JSON reader for large documents) and its test in `tests/support`;
  `spec/tooling.md` §11 (new); `guide/unsafe-and-c.md`, `guide/ceesafec.md`; `tools/cbind_check.py`,
  `tools/package_tests.py`. It amends ADR 0095 §2.1 and §2.6 ("Not part of `ceesafec`") and its
  §7.1's last item ("the tool is not in a release's archives"). No change to the language, the checker, the
  backends, the interpreter, the libraries or the runtime, and no new diagnostic code.

## 1. Context

ADR 0095 specified a generator that reads a C header with clang and writes the `extern "C"` block for it, and
decided (§2.6) that it would be a Python script beside `c2cee.py`, since it is a generator of source and not one of
the compiler's algorithms. That holds for a tree that has a checkout of CeeSafe (CosmoOS). It does not for a program
written against a released compiler: the release's archive is `ceesafec` alone, the book's chapter on calling C can
only say "in CeeSafe's repository", and its readers copy declarations by hand, which is what ADR 0095 was written to
end.

## 2. Decision

```sh
ceesafec cbind --header clock.h -I c -o src/clock.cee
ceesafec cbind --header kernel/handle.h --header kernel/socket.h -I kernel/include --out-dir kernel/bind \
    --config x86_64="--target=x86_64-unknown-none-elf -DCONFIG_DEBUG=1" \
    --config aarch64="--target=aarch64-unknown-none-elf -DCONFIG_DEBUG=1"
```

- **What.** `tools/cbind.py` in CeeSafe, as a command of `ceesafec`: the same options, the same reading of clang's
  preprocessor output and JSON AST (`-Xclang -ast-dump=json`), the same declarations, comments and order. What it
  writes is ADR 0095's §2.2 to §2.4 and §7.1, unchanged; `spec/tooling.md` §11 is now where the command is
  specified. No Python is run.
- **The same bytes.** For the same arguments and the same clang, the command writes what the script writes, byte for
  byte, except the generator's name in the file's first line (`// GENERATED by ceesafec cbind (CeeSafe ADR 0095)
  from …`, where the script says `tools/cbind.py`). The output is laid out by `ceesafec fmt`'s formatter, called in
  the process; `--no-fmt` writes the generator's own layout.
- **The options** are the script's: `--header` (repeatable), `-I`, `-D`, `--target`, `--config NAME=FLAGS`
  (repeatable), `--only`, `--with`, `--leave`, `--no-fmt`, `-o`, `--out-dir`; a value is the next argument, or
  attached (`--header=h`, `-Idir`, `-DNAME`, `-ofile`). The script's `--clang` (and `$CLANG`) is `--cc` here.
- **The C compiler** is the one `ceesafec build` runs (tooling.md §8.1): `--cc`, else `$CC`, else `cc` (on Windows
  clang, gcc, cl, in that order), run as `build` runs it (on Windows through Visual Studio's environment when it
  needs it). It must be clang: gcc and MSVC have no JSON AST. The command asks it (`--version`), and when it is
  not clang and none was named, it uses `clang` from `PATH` if there is one, so that the command works on a Linux
  whose `cc` is gcc and which has clang installed. Otherwise it refuses, in the driver's words:
  `ceesafec: cbind reads clang's AST (-Xclang -ast-dump=json), and the C compiler 'cc' is not clang: install clang,
  or name it with --cc (tooling.md §11)`.
- **Exit status.** 0 when the files are written. 2 for a usage error (the message, then the command's usage, on
  standard error) and for a C compiler that is not found, cannot be run or is not clang (the message alone), as
  `build` exits for these. 1 when the command line is right and the header is not: it is not under any `-I`
  directory, clang cannot read it (clang's words follow, at most 4,000 characters), `--only` names what is not
  declared, a `--with` file cannot be read. Nothing is written in any of these cases. The script exits 1 for all of
  them but the errors its argument parser finds itself (2).
- **`ceesafec cbind --help`** prints the command's own usage and options, as `ceesafec test --help` does;
  `ceesafec --help` lists the command.
- **`tools/cbind.py` stays**, for now, as the oracle of `tools/cbind_check.py` (AGENTS.md: expected values come
  from oracles outside the code under test): the check runs both for every case and requires the same bytes. The
  guide and ADR 0095 point users at `ceesafec cbind`. A change of what is generated is made in both, or the check
  fails. The script is retired when the command's output has its own expectations for every row of ADR 0095's table
  that the comparison now covers; that is a later decision.

### 2.1 The JSON reader

Clang's dump of a header that includes a system's headers is tens of megabytes (`<sqlite3.h>` with macOS's SDK: 2.6
MB; a header that includes CoreFoundation, Security and CoreGraphics: 125 MB). The compiler had one JSON reader
(`src/support/json_reader.cee`, for the language server's and the MCP server's requests): correct, linear, but built
for small documents. A node there owns three vectors (its text, its key, its
children), strings are decoded as they are read, and nesting is limited to 64 levels, which clang's dump of an
expression passes.

`src/support/json_tree.cee` is a second reader for large documents, with the same grammar (RFC 8259; it reuses the
first one's string decoder):

- A node is a span: its kind, where its text is in the document, where its key is, its first child and its next
  sibling, 32 bytes. The document's bytes are kept, and a string is decoded only when it is asked for.
- It takes a list of keys: an object's member with any other key gets no node, and its value is skipped where it
  stands (its brackets and strings are followed; nothing else of it is checked). The command keeps 24 keys (`id`,
  `kind`, `name`, `inner`, `loc`, `range`, `type`, `qualType`, …) and so drops line numbers, offsets, value
  categories and mangled names, most of the dump.
- One pass over the bytes, without recursion: an explicit stack of the open arrays and objects. Neither the size
  nor the depth of the document is limited, except that a document of 4 GiB or more is refused (positions are 32
  bits).

The dump is dropped as soon as a configuration's declarations are made, so the command holds one dump at a time,
whatever the number of headers and configurations. Measured: §4.

## 3. Alternatives

- **Ship `tools/cbind.py` in the release's archive.** Rejected: it needs Python, a second runtime to install and to
  keep in step with the compiler's keyword list and formatter, and Windows users have neither by default.
- **libclang or a C parser of our own instead of the JSON dump.** Rejected for now: libclang is a native dependency
  of the compiler, which has none, and a C parser with the preprocessor and every target's ABI is clang. The JSON
  dump is undocumented and changes between clang versions (ADR 0095 §4), which the fixture's check finds.
- **Extend the existing JSON reader instead of adding one.** Its tree owns what it reads, which the language server
  and the MCP server rely on (they keep nodes after the request's text is gone). Raising its depth limit and making
  its nodes spans would change both users for a document shape they never see.
- **A streaming reader with no tree at all.** The generator comes back to nodes (a typedef names a struct declared
  earlier; functions and macros are written after all types), so it would keep its own copy of each node it may
  need, which is the tree again, less simply.
- **`--clang` beside `--cc`.** Rejected: one option names the C compiler in every command.
- **Refuse whenever `cc` is not clang, without looking for `clang`.** Simpler, and it would make the command fail by
  default on most Linux installations that have clang, with a message that tells the user to type what the command
  can find by itself.
- **Fix the generator's known faults while porting** (§5). Rejected here: the port is checked by comparison with the
  script, and a behaviour change made in one of the two only would hide in the comparison's exceptions. They are
  listed for a change of both.

## 4. Tests and measurements

Run on macOS 27 arm64, Apple clang 21, 2026-11-13, with the compiler of this branch, unless another host is named.

- `python3 tools/cbind_check.py --ceesafec out/ceesafec`: every case the check had (one configuration, two headers,
  two configurations, `--leave`, `--only`, `--with`, a header that does not compile) now runs both generators and
  compares the files; added: the book's `clock.h` (and its committed `clock.cee`), `--no-fmt` (on a declaration
  longer than a line, so that the two layouts differ), `--target` for a bare-metal x86-64, a bare-metal AArch64 and
  Windows (where an enum is `i32`); the command's `--help`, twelve usage errors (exit status 2, nothing written),
  the attached option forms, a header and a `--with` file that are not found (1), a compiler that is not clang by
  `--cc` and by `$CC`, one that cannot be run (2), no compiler named, and `--cc` before `$CC`. 20 files compared, 0
  problems. With the script's `unsigned int` mapped to `i32`, the first failure is the comparison of the first file.
- The same check on Linux x86-64 (Ubuntu 24.04, clang 18.1.3, `cc` is gcc; the tree built there by ceesafec
  0.37.0): the 20 files are the same, the command finds `clang` on `PATH` when none is named, and the 6 problems
  are §5 item 1's, which main has there too.
- `tests/support/run-pass/json-tree.cee`: the reader against Python's `json` (`tools/oracles/json_tree.py`) on 34
  documents, 16 of them not JSON, whole and with a list of keys, and an array nested 200,000 deep; with
  `--check-leaks`.
- Not in the repository (they need a system's headers): 31 headers of macOS's SDK (`stdio.h`, `sqlite3.h`,
  `curl/curl.h`, `mach/mach.h`, `libxml2/libxml/tree.h`, …), each formatted, with `--no-fmt` and for an x86-64
  target: 93 files, all the same bytes as the script's. Twelve of them at once (`--out-dir`) plain, with three
  configurations, with `--leave`, with `--with` and with `-D`: 72 files, all the same.
- Time and peak memory, the whole command (clang's three runs included; clang alone needs 66 MiB and most of the
  time for the last header):

  | header | clang's dump | `tools/cbind.py` | `ceesafec cbind` |
  |---|---|---|---|
  | `sqlite3.h` | 2.6 MB | 0.43 s, 53 MiB | 0.23 s, 26 MiB |
  | `curl/curl.h` | | 0.47 s, 72 MiB | 0.30 s, 28 MiB |
  | `mach/mach.h` | | 0.71 s, 93 MiB | 0.35 s, 30 MiB |
  | CoreFoundation, Security, CoreGraphics, sqlite3, curl, libxml2, mach, ncurses in one header | 125 MB | 3.4 s of CPU, 613 to 640 MiB | 1.0 s of CPU, 168 to 170 MiB |

  The last row's 168 MiB are the dump itself (125 MB) and its tree. A 173 MB dump took 1.2 s of CPU and 234 MiB:
  time and memory grow with the document, not faster.

## 5. What the port found in the generator

Faults of `tools/cbind.py` that the command reproduces, since it writes the same bytes. Each is a change for both.

1. **A `va_list` parameter where `va_list` is a struct** (the x86-64 System V ABI: Linux and macOS on x86-64):
   clang spells the fixture's `__builtin_va_list ap` as `struct __va_list_tag *`, the generator declares the
   function with `*mut __va_list_tag` and the opaque `struct __va_list_tag;`, and `ceesafec` then refuses the file
   (N0292, a name reserved by the C standard). On Apple's arm64, `va_list` is `char *` spelled
   `__builtin_va_list`, which has no typedef in the dump, so the function is left out, as ADR 0095 means. This is
   why `tools/cbind_check.py` reports 6 problems on Linux and on an x86-64 Mac and none on an arm64 Mac, on main
   and on this branch alike: `fx_vprint` is declared (1), the comment that says why it is left out is missing (2),
   and the four programs over the fixture's bindings do not build (3 to 6). Seen with Apple clang 17 on an x86-64
   Mac (the script alone, on main's files) and with Ubuntu's clang 18.1.3 on x86-64 Linux (this branch: the same 6,
   and all 20 files the same in both generators). Nothing else in the check depends on the platform: not clang's
   version, not the system's header paths, not `--target`.

   **Fixed (2026-11-13), in both.** A type whose name the C standard reserves (`__…`, or `_` and an uppercase
   letter: the rule of N0292, type-system.md §28.2, `checkCName` in `src/check/ffi.cee`) has no CeeSafe spelling.
   Neither generator names one any more, whether by its tag (`struct __va_list_tag`), through a typedef of it, or
   by a typedef that is its only name, so what needs the type is treated as anything else CeeSafe cannot spell: a
   function is left out with its comment (`a function with a parameter CeeSafe cannot take`), `extern` data
   likewise, a struct with such a member is opaque for that member, and no opaque `struct __…;` is written for the
   type. A struct, union, enum or function pointer typedef of that kind that the header itself defines is not
   declared, and is listed under `// Not declared:` (`a type whose name C reserves`). The fixture has such types
   of its own (`struct __fx_reserved`, `struct _Fx_reserved`), so the check fails without the fix on every
   platform (17 problems on an arm64 Mac), not only where `va_list` is a struct. Not changed: a function, datum,
   member or enumerator whose own name is reserved, and names N0292 refuses for its other reasons (a C keyword,
   the runtime's `cee_…`), are still written as before.
2. **Output that is not UTF-8.** The script reads clang's output as text and stops with a Python traceback
   (`UnicodeDecodeError`) when the preprocessed text has a byte that is not UTF-8 (found with a header that includes
   CoreServices from macOS's SDK: a 0xA9 byte). The command reads bytes and writes the binding. The one case found
   where the two differ in whether they succeed.
3. **Errors that are tracebacks in the script**: a `--with` file that does not exist, a `--config` whose flags have
   an unclosed quote. The command says what is wrong (exit status 1 and 2).
4. **`-o` not named `.cee`** is refused by the script only after the unformatted file is written (`ceesafec fmt`
   takes `.cee` files). The command formats the text before it writes, whatever the name.
5. **A name that is declared twice by the preprocessor** is searched for in a list (`name not in names`): the
   macros of a header are read in time quadratic in their number, in both. 1,000 macros are not noticed.

## 6. Compatibility

A new command: no program changes. `tools/cbind.py` and its options are unchanged, and a tree that runs it keeps
working. A file the command writes differs from one the script wrote in the first line only, so a tree that
regenerates its bindings in CI (ADR 0095 §2.5) and moves from the script to the command sees one changed line per
file, once.
