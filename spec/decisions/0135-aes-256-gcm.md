# ADR 0135 — Aes256Gcm, on the CPU's AES and carry-less multiply instructions

- Status: **Accepted** by the owner, 2026-11-14 ("I accept all ADRs as recommended": the four answers proposed in
  §6). To be implemented on branch `impl/0135`; until then a prototype of the runtime functions exists outside the
  tree and is what §7 measures. Raised by CosmoStore's CEESAFE_GAPS G33
  (`~/dev/CeeSafeApps/cosmostore/CEESAFE_GAPS.md`): its server-side encryption (CosmoStore ADR-0046) is designed
  and waits for a cipher, and CosmoStore calls no C.
- Scope: `lib/std` (a new `Aes256Gcm`, in a new `lib/std/ciphers.cee`), `runtime/hosted/ceesafe_rt_io.c` and
  `runtime/include/ceesafe/rt.h` (four functions), the interpreter's C library model (`src/interpreter/io.cee`),
  `spec/api/std.md`, the guide and the book's Appendix on lib/std. No language, checker or emitter change.

## 1. Context

- **What lib/std has.** Checksums and digests (`Crc32c`, `Crc64Nvme`, `Md5`, `Sha256`, `HmacSha256`; ADR 0075) and
  the system's random source (`Random.fill`, ADR 0060). Nothing encrypts.
- **What an application cannot do well itself.** AES by table lookup leaks its key through the cache; AES without
  tables in portable code runs at a few MB/s; GHASH without a carry-less multiply is slower still. A storage
  server moves GB/s (ADR 0089's CRC-32C is 8 GB/s on an M1).
- **What the CPU offers.** x86-64: AES-NI (`aesenc`, `aesenclast`, `aeskeygenassist`) and `pclmulqdq`, on every
  server and desktop CPU since about 2010 (Westmere, Bulldozer); not in the x86-64 baseline. AArch64: the AES
  extension (`aese`, `aesmc`, and the 64-bit `pmull`), on every Apple arm64 CPU, Graviton, Ampere and most
  Cortex-A cores; optional in ARMv8.0, and absent from some boards (the Raspberry Pi 4's Cortex-A72 has none).
  So, as for CRC-32C, the instructions must be asked for at run time.
- **Why AES-256-GCM.** It is what S3's server-side encryption, TLS 1.3 and most storage formats name. It
  authenticates as it encrypts, so a changed byte is refused and not returned. One algorithm, one key size: the
  application has nothing to choose wrongly.
- **Measured** (§7), 64 MiB sealed, best of five:

  | | M1 (macOS, Apple clang 21) | x86-64 build of the same file, run under Rosetta on that M1 |
  |---|---:|---:|
  | the prototype's `seal`, 64 KiB at a time | **3,049 MB/s** | 1,951 MB/s |
  | its two halves alone: counter mode; GHASH | 5,532; 6,556 MB/s | 4,662; 3,367 MB/s |

  The x86-64 column is a translation, not a CPU: it shows the code is right there, not how fast it is. No x86-64
  CPU, no gcc and no Linux was run (§5).

## 2. Proposal

### 2.1 `Aes256Gcm` (`lib/std/ciphers.cee`)

```
public struct Aes256Gcm { … }                       // the expanded key; wiped when it is dropped

impl Aes256Gcm {
    /// A cipher for `key`; null unless the key is 32 bytes.
    public fn create(key: Slice<u8>) -> Aes256Gcm?;

    /// Encrypts `data` in place and returns the tag of `associated` and the ciphertext.
    public fn seal(borrow this, nonce: [u8; 12], associated: Slice<u8>, data: SliceMut<u8>) -> [u8; 16];

    /// Checks `tag`, in constant time; true and `data` decrypted in place when it is theirs, false and `data`
    /// zeroed when it is not.
    public fn open(borrow this, nonce: [u8; 12], associated: Slice<u8>, data: SliceMut<u8>, tag: [u8; 16]) -> bool;
}
```

- **In place, no allocation, no error:** the only refusals are a key of the wrong length (null) and a tag that
  does not check (false). All three functions are `@effects()`: async code and a `drop` block may call them.
- **`open` gives back nothing it did not authenticate:** the tag is checked over the ciphertext first; only then
  is the text decrypted. On false the bytes are zeros, so a caller that forgets to look at the answer has no
  plaintext to use.
- **The nonce is the caller's.** GCM is broken by one nonce used twice under one key: the documentation says so
  first, and shows the two safe ways (a counter under a key used for one thing; a fresh key per object).
  `Random.fill` gives nonces and keys. One call seals at most 2^36 - 32 bytes (GCM's limit); a longer slice is a
  panic, as an index out of range is.
- **The key is wiped:** `Aes256Gcm` has a `drop` block that zeros its expanded key.
- **Beside it,** since every user of a cipher needs it and CosmoStore wrote its own: `ConstantTime.equal(a, b) -> bool`
  in `lib/std`, which compares two slices in time that depends only on their lengths. (Proposed and accepted as
  `Bytes.equal`; renamed while building, since the compiler's own sources have a `Bytes` and a lib/std name would
  collide with every package that has one. The owner may name it otherwise before 0.45.0.)

### 2.2 Four runtime functions (`ceesafe_rt_io.c`, declared in `rt.h`)

| Function | Does |
|---|---|
| `uint32_t ceesafe_aes256gcm_available(void)` | 1 when the CPU has the instructions, else 0. Asked once per process, then a relaxed atomic load |
| `void ceesafe_aes256gcm_expand(const uint8_t *key, uint8_t *schedule)` | from 32 key bytes, 304 bytes: 15 round keys, the GHASH key and three powers of it |
| `void ceesafe_aes256gcm_seal(schedule, nonce, aad, aadLength, data, length, tag)` | encrypts `data` in place, writes 16 tag bytes |
| `uint32_t ceesafe_aes256gcm_open(schedule, nonce, aad, aadLength, data, length, tag)` | 1 and the plaintext in place, or 0 and `data` zeroed |

- **How the CPU is asked,** as ADR 0089 §2.1 asks for CRC-32C: `cpuid` leaf 1 (PCLMULQDQ, SSSE3, AES) on x86-64;
  on AArch64 the compiler's target (`__ARM_FEATURE_AES`), else `sysctlbyname("hw.optional.arm.FEAT_AES"` and
  `…FEAT_PMULL")` on macOS, `getauxval(AT_HWCAP)` (AES and PMULL) on Linux,
  `IsProcessorFeaturePresent(PF_ARM_V8_CRYPTO_INSTRUCTIONS_AVAILABLE)` on Windows; anything else: 0.
- **How the instructions are reached:** the compiler's intrinsics (`<immintrin.h>`, `<arm_neon.h>`), in functions
  marked with a target attribute (`target("aes,pclmul,ssse3")`; `target("aes")` on clang and `target("+crypto")` on
  gcc for AArch64 when the target lacks it), so no file needs a flag. MSVC needs no attribute. Two things a Linux
  build showed (§7.3): gcc to 12 declares AESE and PMULL under `+crypto`, not `+aes`; and clang before 16 declares
  them on AArch64 only when the whole file is compiled for them, so there, without `-march=…+aes`, the probe
  answers 0 and lib/std's own code runs (clang 14 is Debian 12's and Ubuntu 22.04's; their gcc takes the fast
  path). This is where it
  parts from ADR 0089, which used inline assembly for one instruction: AES-GCM is some sixty vector operations,
  and intrinsics are what every compiler checks and schedules. **(Question 1.)**
- **What they do:** counter mode eight blocks at a time (the rounds of eight blocks side by side); GHASH four
  blocks per reduction, with the key's first four powers; SubWord of the key schedule by the instruction, not a
  table. Nothing branches on, or indexes memory by, a key, a nonce or the data.
- **Contract** (AGENTS.md, a C adapter behind a documented one): each reads and writes only the lengths it is
  given, during the call; keeps no pointer; allocates nothing; cannot fail. The three that work are called only
  after `available` said 1; elsewhere they do nothing and `open` answers 0.

### 2.3 Where the CPU has no such instructions: constant-time code in CeeSafe

`create` asks `ceesafe_aes256gcm_available()` once and remembers the answer. On 0, `seal` and `open` run lib/std's
own AES-256-GCM, written in CeeSafe with no table indexed by a secret: the S-box as a circuit of XOR and AND over
the block's bits, GHASH as a shift-and-add multiply with masks instead of branches. The results are the same
bytes. It is slow, about 16 MB/s on the M1 (measured on the code as built, compiled with `-O2`): a correct answer
for a board without the extension, not a fast one. **(Question 2.)**

### 2.4 The interpreter

Its C library model answers `ceesafe_aes256gcm_available` with 0, so interpreted programs run §2.3's code, as on
a CPU without the instructions; the other three are modelled to do nothing and answer 0, so no call can fault.
The corpus therefore runs both implementations against the same expected bytes: compiled, the instructions (where
the machine has them); interpreted, the CeeSafe code.

## 3. Alternatives considered

- **A. A table-driven AES in lib/std** (fast in software, 100 to 200 MB/s): its lookups are indexed by key and
  data, which a neighbour on the machine can time. Not something to ship as the default of a memory-safe language.
- **B. No fallback:** `create` is null without the instructions. Simple, but a program then needs a second cipher
  for some machines, which is what a standard library is there to spare it.
- **C. ChaCha20-Poly1305 instead, or as the fallback:** constant-time and fast in portable code, and a good
  second cipher; but it is not what S3, or a peer that asks for AES-256-GCM, speaks, and a fallback that writes
  another format is not a fallback. A later ADR. **(Question 3.)**
- **D. Language intrinsics** (ADR 0089's alternative A): still the right home for SIMD, still a larger design
  than one cipher needs; lib/std could move onto them without an API change.
- **E. Linking a library** (OpenSSL, as `web_tls` does for TLS): a dependency, a C toolchain and a licence for
  every program that seals a buffer; and the kernel profiles cannot link it.
- **F. One pass over the data** (hash each ciphertext block as it is made): about twice the rate of §7's two
  passes on long buffers. A follow-up when a profile asks for it, as ADR 0089 left its three chains; the API does
  not change.

## 4. Not in this ADR

- AES-128 and AES-192, other modes (CBC, CTR alone, XTS, SIV), ChaCha20-Poly1305.
- A streaming form (seal a long input in pieces under one nonce): callers seal chunks, each with its own nonce,
  as CosmoStore ADR-0046 does with 64 KiB.
- Key derivation (HKDF, PBKDF2) and key wrap; `HmacSha256` is there for the first.
- SHA-256 by instruction, AVX-512 and VAES.
- Kernel profiles: lib/std is hosted only (ADR 0026).

## 5. Testing

- **Expected bytes from outside the code under test:** the four AES-256 test cases of the GCM specification
  (McGrew and Viega; NIST's test cases 13 to 16), and cases from `tools/oracles/aes_gcm_model.py`, AES-256-GCM
  written from its definitions in Python, which checks itself against those four cases and against 300 random ones
  from Python's `cryptography` (which is OpenSSL) where that package is installed.
- **The corpus:** `run-pass/aes-gcm.cee`, written by `tools/oracles/gen_aes_gcm_cases.py`: two of the
  specification's cases (15 and 16) and four rounds, texts of 0 to 129 bytes with and without associated data,
  each sealed, opened and tampered with (one bit of the tag, of the ciphertext, of the associated data or of the
  nonce: refused, with `data` zeroed), printing what the oracle printed; compiled and interpreted (§2.4). Keys of
  0, 16, 31, 33 and 64 bytes are null. It is short because the interpreter runs the bit-sliced code some thousand
  times slower than compiled code (a 1 KiB `seal` takes 3 s, this program 6 s), and the corpus runs every program
  in it. `check-fail/aes-gcm-arguments.cee`: a buffer that cannot be written, a nonce of 8 bytes and a tag of 8
  bytes are not programs (N0205, N0248).
- **The long list, compiled only:** `tools/aes_gcm_check.py`, a step of the contract suite ("cipher"), builds the
  same program with all four cases and 105 rounds: associated data of 0 to 257 bytes with texts of every length
  around one, four and eight blocks, to 1,000 bytes, then 4 KiB and 64 KiB and a byte either side. For this
  machine, and on Apple silicon for x86-64 too, run by Rosetta.
- **lib/std's own code, compiled:** a machine with the instructions never runs it, since the probe picks them.
  It is run compiled where the probe says 0: by clang 14 on Linux arm64 (§7.3), the long list; and it was built
  and run alone while it was written (§7.1).
- **The runtime functions alone,** in a C harness (§7.2), on each compiler and architecture a machine is had for.
- **The CeeSafe code's S-box** against the 256 values of the algebraic definition, in the oracle.
- **Strict warnings:** `ceesafe_rt_io.c` under c-backend.md §1's set with `-Werror`.
- **Covered since (§7.3, §7.4):** Linux and gcc, a real x86-64 CPU, and MSVC for ARM64 and for x64.
- **Not covered by a machine:** MSVC's x64 build on a real x86-64 CPU (it ran in Windows on Arm's translation),
  and an AArch64 or x86-64 CPU without the instructions (lib/std's own code compiled ran where the C compiler
  left them out).

## 6. Questions for the owner

Answered on 2026-11-14, each as proposed: (1) runtime functions with intrinsics under a target attribute and a
run-time probe; (2) constant-time CeeSafe code where the CPU has no such instructions; (3) `Aes256Gcm` and
`Bytes.equal` (built as `ConstantTime.equal`, §2.1) alone; (4) `fix/cee-proxy-findings` released now as 0.44.1,
this ADR as 0.45.0 once it is built and run on x86-64 and Linux.

1. **Mechanism:** runtime functions with intrinsics under a target attribute and a run-time probe (proposed), or
   inline assembly as ADR 0089, or wait for language intrinsics (D)?
2. **Without the instructions:** slow constant-time CeeSafe code (proposed), a fast table-driven AES (A), or null
   (B)?
3. **Scope:** `Aes256Gcm` and `Bytes.equal` alone (proposed), or ChaCha20-Poly1305 with them (C)?
4. **Release:** the owner asked on 2026-11-14 that `fix/cee-proxy-findings` (six commits, on `main`'s head) be in
   the next release. Release that branch now as 0.44.1, and this ADR as 0.45.0 once it is accepted, built and
   run on x86-64 and Linux (proposed, given "we need to speed up the release cycle"); or hold both for 0.45.0?

## 7. The prototype and its evidence (2026-11-14)

### 7.1 What exists

The runtime section of §2.2 as one C file, with stand-ins for `ceesafe_atomic_*` and `ceesafe_mem_*`, and a
harness; the prototype is not in the tree. Since the answers, the tree has the section in `ceesafe_rt_io.c`,
`lib/std/ciphers.cee` with the CeeSafe code of §2.3, the interpreter's model, the oracle and the corpus programs
of §5; the CeeSafe code was first built and run alone, against the specification's four cases and 150 from
OpenSSL, and its S-box circuit against all 256 inputs.

### 7.2 Runs (M1, macOS, Apple clang 21.0.0; load average 3 to 8, other sessions)

- **Correct:** the four test cases of the specification; 20,200 cases from `cryptography` 50.0.2 (OpenSSL 4.0.3):
  200 at fixed lengths (associated data of 0 to 257 bytes, text of 0 to 65,537 bytes, around every boundary) and
  20,000 random; `seal` gives the oracle's ciphertext and tag and `open` gives the text back, 0 mismatches.
  80,800 tamperings (four per case), each refused with the buffer zeroed.
- **On two architectures:** built for arm64, and built for x86-64 (`-arch x86_64`) and run under Rosetta: the same
  result on both. The x86-64 run exercises the AES-NI and PCLMULQDQ path's logic, in translation.
- **Strict warnings:** `-std=c11 -O2 -Wall -Wextra -Wpedantic -Wshadow -Wconversion -Wsign-conversion`: none, for
  either architecture.
- **Throughput:** §1's table. The first version hashed one block per multiply and ran its rounds in a loop the
  compiler did not unroll: 800 MB/s. Four blocks per reduction: 1,113. A fixed eight-block path: 3,012.
- **Not run:** everything §5 lists as not covered.

### 7.3 After the answers: lib/std's `Aes256Gcm`, and Linux (2026-11-14)

- **Through lib/std** (a CeeSafe program sealing 64 KiB 16,000 times, `ceesafec build`): 3,139 MB/s on the M1,
  the prototype's speed.
- **Linux, in containers on that M1** (Debian 12; gcc 12.2.0 and clang 14.0.6; arm64 natively in the virtual
  machine, x86-64 in translation): the long list's program, as C emitted by ceesafec, built with each compiler
  and run: its 329 lines are the oracle's on all four. Throughput of the same 64 KiB program there: arm64 gcc
  1,122 MB/s, arm64 clang 14 15 MB/s (lib/std's own code, see §2.2), x86-64 gcc 1,101 and clang 1,162 (in
  translation). `ceesafe_rt_io.c` with gcc under the strict set: no warning on either.
- **Two faults these runs found, fixed:** gcc 12 on AArch64 refused the functions marked `target("+aes")` (now
  `+crypto`), and clang 14 there cannot use the intrinsics in a marked function at all (now left out, §2.2).
- **One slow spot found, fixed:** gcc at `-O2` does not unroll the eight-block loop, so the blocks went through
  memory one by one: 546 MB/s on arm64. With the eight blocks named: 960 to 1,122 (and no loss with clang).
- **A fault in a finished build that the type checker hid:** a library function with `unsafe` and no `Safety:`
  line (N0283) left `Aes256Gcm.create` unusable, reported at its callers as N0222, "its library body has an
  error", while `ceesafec build` of the compiler and `spec_check` passed. The contract suite's "library" step
  (`check --library-diagnostics`) checks the library with its own diagnostics on; it was not run on that build.

### 7.4 A real x86-64 CPU, and MSVC (2026-11-14, the owner's hosts)

- **x86-64, natively** (AMD Ryzen 5 PRO 3600, Debian 12, gcc 12.2.0): the long list's program, as C emitted by
  ceesafec: its 329 lines are the oracle's. 1,430 MB/s. `ceesafe_rt_io.c` under gcc's strict set: no warning;
  with `-D_FORTIFY_SOURCE=2 -Wall -Werror`: builds.
- **MSVC** (Visual Studio 18, Windows 11 on Arm in a virtual machine; `cl /std:c11 /O2 /W3`), the same program:
  for ARM64, natively, and for x64, run by Windows' translation: 329 lines as the oracle's on both, no warning.
  Throughput: 1,000 MB/s (ARM64), 759 (x64, translated).
- **A fault this found, fixed:** MSVC's `vmull_p64` takes its two polynomials as vectors of one, not as integers
  (C2440): the three low-half products now go through a macro with MSVC's form.
- **lib/std's own code under MSVC** (the same program built with the two branches left out): the same 329 lines
  on both architectures; 3 MB/s on ARM64, 2 on x64 in translation, where clang gives 15.
